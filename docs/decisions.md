# ModelFit 설계 결정 기록

## 1. Phase 1에서 규칙 기반 분석기를 먼저 사용하는 이유

**결정:** `RuleBasedPromptAnalyzer`를 기본 분석기로 사용한다.

외부 LLM API를 호출하면 API 키, 비용, 지연, 오류 처리 등 많은 의존성이 생긴다.
Phase 1 MVP의 목표는 추천 파이프라인 전체가 작동하는지 검증하는 것이다.
규칙 기반으로도 작업 유형·복잡도·필요 기능을 충분히 추정할 수 있으며,
결과의 정확도보다 시스템 흐름의 완전성을 먼저 확인한다.

LLM 분석기는 `PromptAnalyzer` 인터페이스를 구현하므로 팩토리 함수만 변경하면 교체 가능하다.

## 2. 모델 카탈로그를 코드와 분리한 이유

**결정:** 카탈로그 데이터를 `model-catalog.seed.ts`에, 추천 알고리즘을 별도 파일에 작성한다.

모델 정보(이름, 가격, 기능)는 자주 변경되지만 알고리즘은 상대적으로 안정적이다.
데이터와 알고리즘을 같은 파일에 두면 변경 이유가 두 가지가 되어 단일 책임 원칙을 위반한다.
또한 나중에 카탈로그를 DB나 외부 API로 교체할 때 알고리즘 파일을 건드리지 않아도 된다.

## 3. 모델 점수를 절대적인 성능 순위로 간주하지 않는 이유

**결정:** 점수는 "해당 프롬프트에 대한 상대적 적합도"이며, 모델의 절대 품질이 아니다.

모델 성능은 벤치마크마다 다르고, 실제 사용 사례에 따라 크게 달라진다.
특히 `taskScores`는 공개된 벤치마크를 기준으로 편의상 입력한 수치이며,
동일 작업에서도 프롬프트 스타일, 언어, 복잡도에 따라 결과가 달라질 수 있다.

이 때문에 추천 이유는 내부 필드명(`taskFit: 0.8`)을 노출하지 않고
사용자가 이해할 수 있는 문장으로 변환한다.

## 4. 실제 무료 실행 기능을 Provider Adapter 뒤로 분리한 이유

**결정:** 추천과 실행을 완전히 분리한다. 추천은 정보를 제공하고, 실행은 별도 Provider Adapter가 담당한다.

추천 단계에서 실제 모델을 호출하면 추천 결과가 Provider Adapter의 가용성에 종속된다.
예: Gemini API가 다운되면 Gemini 모델 추천 자체가 실패하게 된다.
두 관심사를 분리하면 추천은 항상 정보를 제공하고, 사용자가 선택 후 실행을 시도하도록 설계할 수 있다.

## 5. 외부 서비스 없이도 로컬 실행 가능하게 한 이유

**결정:** Phase 1은 Supabase, Redis, Gemini, OpenRouter 없이도 완전히 동작한다.

MVP 개발 단계에서 외부 서비스에 의존하면 환경 설정 문제로 개발이 중단될 수 있다.
메모리 구현체와 시드 데이터를 먼저 만들고 외부 서비스는 인터페이스 교체로 연결한다.
테스트도 외부 API를 호출하지 않아 빠르고 안정적으로 실행된다.

## 6. Zod v4 적용 시 변경사항

**결정:** Zod v4을 사용한다.

- `z.record()`: 키 타입과 값 타입 두 인수 필요 → `z.record(z.string(), z.unknown())`
- `error.errors` → `error.issues`
- 그 외 API는 v3과 거의 동일

## 7. 모델 데이터 검증 원칙

**결정:** 확인되지 않은 수치는 임의로 작성하지 않는다.

`taskScores`는 공개 벤치마크를 참고한 편의상 수치이며, `lastVerifiedAt`으로 검증 시점을 명시한다.
가격·무료 한도 등 변동 가능한 값은 `limitations` 필드에 주의사항으로 포함한다.
`contextWindow`가 불명확한 모델은 `undefined`로 두었다.

## 8. 동점 처리 결정성

**결정:** 점수 차이 5점 미만 시 안정성→속도→컨텍스트→비용→모델ID 순으로 결정한다.

마지막 조건으로 모델 ID 오름차순을 사용하여 동일 입력에 대해 항상 같은 결과를 반환하도록 한다.
이는 테스트 재현성을 보장하기 위한 것이다.
